I design for the data you'll have next year

My career started with CRM dashboards and KPI reports, where the numbers grow every single day. That taught me to treat data as the heart of a feature, and to plan for growth before it arrives.

Data people can act on. From CRM dashboards and KPI reports backed by C# and MySQL APIs, to Gantt timelines where due dates become something you can see and move, I build features that turn records into decisions.

Scalability. Solutions design work taught me to plan structure before code: how the data is shaped, how it will be queried, and which parts will grow fastest. Document databases like RavenDB let that structure evolve without painful migrations.

Performance. A report only helps if it opens quickly. I shape queries and indexes around how people actually read the data, and move heavy work out of the request when it can run in the background.

Reliability. I use Serilog for structured logging, so when something breaks, the logs say what happened and where. Grafana and Datadog dashboards let us watch systems in production and spot problems before users report them. Moving systems from .NET Framework 4 to .NET 6 kept them on a supported, patched platform.

Security. At Commit Works, I work within ISO/IEC 27001 information security practices, so protecting data and access is part of how features are built, not a step at the end. And nothing ships unreviewed, including the code Claude writes.

I put AI to work, then review its homework

At Commit Works, I brought LLMs into our development lifecycle. The trick isn't letting AI write code. It's giving it a clear spec and never letting it merge alone.

feature/spec-driven-workflow
  1. specWhat the feature must do, written down first
  2. planHow it fits into the existing system
  3. tasksSmall steps, each easy to review
  4. codeClaude writes the code and bug fixes
  5. reviewOur team reads every line before it merges

I used GitHub Spec Kit as the template for the workflow. Every change starts from a spec, a plan, and a task list before Claude writes anything.

Its biggest test so far was converting a legacy Ext JS application to Angular, a full framework rewrite rather than a version bump.

Specs remove guesswork, so the code that comes back matches what we meant. Small tasks keep reviews honest, because nobody can skim a change they can read in a few minutes.

The result is a team that spends less time on boilerplate and more time on the decisions that shape the product.
